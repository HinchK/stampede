# Subscription-route isolation and user-maintained secret files

Research date: **2026-11-06**. Scope: **Establish enforceable isolation for subscription-backed routes**. Documentation research only; no credentials, accounts, provider sessions, cancellation experiments, or isolation changes were used.

## Conclusion

**By default, keep secret files maintained by the user and unavailable to model-directed tools.** The user explicitly deferred encrypted-storage work. Do not introduce encryption, keyring migration, biometric approval, or a Stampede vault as pilot requirements. Separate legitimate internal use of existing provider authentication from an agent asking a file or shell tool to read, change, copy, or reveal those credentials. In that default mode, secret locations may be referenced by name/path; values must not enter prompts, logs, checkpoints, or handoffs. The accepted per-run exception below is separate from the default isolation researched here.

The practical first candidate is a **pinned Codex subscription route using its existing authentication, managed permissions, restricted tools, and a protected Stampede controller**. Claude Code and AGY have useful documented components but additional tool-surface gaps to close. This is a candidate ordering based on documented controls, not a security certification or model-quality ranking. **No inspected route is verified eligible yet.**

## What primary sources establish

**Existing authentication is compatibility context, not a migration requirement.** Codex supports cached ChatGPT login in an authentication file or an OS credential store; AGY documents reuse of the native OS keyring. Leave the user's existing authentication under their control. These mechanisms permit the provider client to authenticate, but do not prove that its model-directed tools cannot retrieve the same values. Stampede should check non-secret readiness rather than inspect or copy credential contents. [Codex authentication](https://learn.chatgpt.com/docs/auth), [AGY authentication](https://antigravity.google/docs/install?tab=cli).

**Codex.** Current permissions document exact-path read denials, platform-enforced command restrictions, and refusal of unsupported policies. On some platforms, deny-glob matches are captured at process start; later-created matching files may remain accessible to an existing process. Network-domain restrictions require the actual proxy, and command-network policy does not cover every other capability. Use fixed protected directories, not merely a `.env` filename glob, and explicitly restrict connectors/MCP/web capabilities. Managed requirements can constrain permission profiles; app-server supplies interruption, but interruption is not proof all detached or remote effects stopped. [Permissions](https://learn.chatgpt.com/docs/permissions), [managed security examples](https://learn.chatgpt.com/docs/enterprise/security-cookbook), [app-server](https://learn.chatgpt.com/docs/app-server).

**Claude Code.** The documented sandbox covers shell commands and their subprocesses; file/web tools, MCP servers, hooks, monitors, and LSP helpers are outside that shell boundary. Reads normally include much of the host, and subprocesses may inherit secrets. Strict settings, credential denies/scrubbing, and separate tool permissions are necessary. Credential masking can substitute placeholders and inject values through a proxy, but it is shell-specific; file masking differs on macOS, and its unmatched-extraction default can allow unmasked access. A shell sandbox alone therefore cannot qualify the whole route. [Sandbox scope and credential controls](https://code.claude.com/docs/en/sandboxing), [security model](https://code.claude.com/docs/en/security).

**AGY.** CLI sandboxing must be enabled, and documentation says its sandbox flag has no effect when unsupported. Fine-grained rules cover file, command, URL, and other actions, with deny precedence. Automatic outside-sandbox execution is incompatible with a boundary that assumes every model command is contained. Require supported containment, no automatic escape, protected settings, and explicit restrictions on all other tools. [CLI reference](https://antigravity.google/docs/cli/reference/), [permissions](https://antigravity.google/docs/permissions), [terminal sandbox](https://antigravity.google/docs/sandbox?tab=cli).

## Recommended default architecture: three separate authorities

This is an engineering proposal derived from the documented constraints, not an existing Stampede capability.

1. **Human authority and controller.** Keep the grant store, scheduler policy, and protected Git integration outside worker-readable/writable storage, owned by a dedicated controller OS identity. Grant issuance, widening, and revocation use an operator-only entrypoint in the user's outside session; do not expose that administrative endpoint to agent tools. The worker-facing interface accepts scoped work requests, not arbitrary commands or grants. Each operation checks the recorded repository/run, allowed action and target, deadline, revocation state, and requested commit/ref. Protect controller binaries/configuration and prevent worker access to its administrative socket or identity. This requires an actual process/filesystem boundary, not merely a different file or pane name; the concrete host setup must pass the probes below.
2. **Authenticated harness.** The trusted, pinned vendor CLI uses its existing user-maintained subscription login. Its process is part of the trusted computing base; credential refresh does not expose values to the model. Disable unreviewed plugins, hooks, MCP servers, browser profiles, and repository configuration that can add host execution. Herdr still presents and controls these sessions. The route adapter must lock every model-directed tool surface away from controller state, secret files, credential helpers, host processes, other sessions, and configuration that can weaken restrictions. If a harness cannot support that separation, it remains ineligible.
3. **Worker execution.** Model-directed filesystem/shell operations run only in the admitted work area with narrowly allowed networking. No production credentials, host administrator sockets, SSH agents, Docker socket, or writable shared control directories are exposed. Authenticated Git pushes, PR changes, and opted-in base merges go through the controller's limited operations interface, with repository/ref/commit constraints and action-time grant checks. It executes fixed operations, not arbitrary shell supplied by the model; untrusted Git hooks/config must not become controller code execution. Network and credential restrictions must prevent an equivalent direct action bypass.

Provider authentication is not moved to a new model API: API and local-model support remain deferred. A controller request protocol is local orchestration, not a new billing path. A full CLI in a VM with its readable login file does **not** solve the secret-value requirement. Conversely, putting only its shell in a sandbox does not contain privileged built-in tools. Eligibility requires proving the complete split for the pinned route and platform.

In default mode, protect application secrets similarly: the user owns and maintains secret-bearing files. Keep them outside model-readable/writable paths, or explicitly deny all tool access when their location must remain inside a project. A plain `.gitignore` entry or file mode accessible to the worker identity does not satisfy that boundary. Keep non-secret placeholders in generated examples. Adding, changing, or recovering credentials requires the user's outside session; Stampede receives only a readiness result, never values. A trusted application may use the file when authorized, but handing its contents or inherited secret environment to arbitrary model-generated code defeats the separation.

## Accepted opt-in exception: scoped exposure and credential cycling

Subsequent user direction permits an **explicit per-run secret-exposure mode**, limited to named credentials and approved agents/providers. This is a policy exception, not a researched capability of the routes above. No values may enter Git, public output, or routine logs. All unapproved credentials, grant controls, and other host resources remain protected; scoped exposure is not blanket host access.

After approved exposure, Stampede cycles credentials only through supported, explicitly authorized integrations. It verifies the replacement before revoking the old credential where the service supports that sequence; otherwise it guides the human through the service's supported procedure. Record a durable **credential-cycling-pending** obligation until the required replacement/revocation outcome is verified, including after interruption or restart. A task ending or a process exiting must not clear that obligation. Persist identifiers and status, not secret values.

This research did not inspect rotation APIs, establish supported services, or implement exposure, cycling, transcript handling, or verification. Service-specific feasibility and acceptance checks remain required before enabling an integration. Encryption remains outside this pilot's scope.

## Disposable eligibility probes required before unattended use

Use synthetic canary credentials and a disposable repository first; real login verification remains a later operator-authorized task.

- In default mode, attempt secret retrieval through shell, built-in reads/search, environment dumps, credential helpers, symlinks, newly created files, plugins, and nested agents; inspect outputs and logs for canaries.
- Attempt modifying grants, controller binaries, permission settings, hooks, and shared repository control files; attempt forged “human approval” and replayed grant requests.
- Try direct Git push, API-based repository mutation, network exfiltration, and a merge that triggers deployment. Only scoped controller operations may succeed.
- Revoke/expire a grant between admission and side effect. Deny the next action; reconcile already-started effects instead of claiming they were undone.
- Stop parent, child, detached process, background server, and any remote task. Require observed termination or explicit unresolved status before replacement writes begin.
- Restart the harness and controller; ensure saved conversation cannot recreate a grant, and missing isolation fails closed. Verify subscription billing class and no credit/API fallback.

The default probes must continue to block every unapproved credential when an exposure exception is enabled; separately verify named-recipient restrictions, output exclusions, and recovery of pending cycling obligations.

Trust assumptions: the OS, issuer/controller, vendor harness, and approved adapter are trusted; model output, repositories, and worker code are not. Administrator/OS compromise is outside this pilot guarantee. Same-user bypass, secret-file access isolation, full tool coverage, subscription login under locked settings, and remote cancellation remain unverified. Failure of any required probe means the route is unavailable for unattended work, not permission to silently weaken the boundary.
