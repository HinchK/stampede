# Assessing Stampede's proposed model and harness routing

Research date: **2026-11-06**. Ticket: **EHS-11**. Scope: documented capabilities and initial hypotheses, not a benchmark or account audit.

## Conclusion

The proposed team is a reasonable starting experiment. Most assignments have capability support; none establishes a universal winner for Stampede. Recommend a route consisting of **model/version + reasoning effort + harness/version + account/access path + permissions**, then learn from accepted work and human effort. A product name alone cannot establish cost, entitlement, reliability, or suitability.

**Supported** below means a documented capability or vendor recommendation. **Plausible** means an engineering hypothesis worth testing. **Unproven** means the comparative advantage has not been established by the sources inspected.

## Access is a separate decision

Installed does not mean authenticated, subscribed, or entitled to a model. The [provider capability report](2026-11-06-swarm-provider-capabilities.md) records CLI observations and unresolved access/cancellation/accounting contracts. It distinguishes subscription paths from API billing, including Google's consumer CLI migration.

Two routing traps deserve explicit setup checks. OpenCode's Anthropic instructions prescribe API access; do not assume a Claude consumer subscription transfers into arbitrary harnesses. ZCode distinguishes Coding Plan authorization from general API/prepaid access; its documentation describes credit and weekly limits. A long-task harness is not unlimited capacity. [OpenCode providers](https://opencode.ai/docs/providers/), [ZCode connections](https://zcode.z.ai/en/docs/configuration)

## Proposed recommendation method and measurements

These are design recommendations, not measured results:

1. **Filter for eligibility first:** required tools, allowed actions, supported account path, available quota, continuity, cancellation, and structured evidence. Treat unknown availability as unknown, not free capacity.
2. **Start simply:** generalist worker, stronger planner when justified, and a separately scoped reviewer. Try inexpensive specialists on bounded research/docs/edits. Add workers only for independent useful work within shared budgets.
3. **Compare matched tasks:** same starting commit, acceptance criteria, context, tools, and budget. Pin model/effort/harness versions. Hold the model fixed when comparing harnesses where supported; otherwise label the result a whole-system comparison. Repeat runs and reserve held-out tasks before promoting a routing rule.
4. **Optimize accepted outcomes per human minute:** include setup, interruptions, review, repairs, retries, coordination, and harness-improvement overhead. Track elapsed time, defects, verified completion, recovery success, and attributable API spend or subscription consumption separately.
5. **Record token velocity over time:** input/output, cached and reasoning tokens where exposed; model-active, tool-wait, queue, and wall time; quota/reset observations and provenance. Report output tokens per generation second only when generation timing exists; otherwise label tokens per elapsed second as effective throughput. Unknown fields stay missing. Different tokenizers, hidden reasoning, caching, parallelism, and billing units prevent raw tokens/second from ranking cross-provider efficiency. Pair velocity with accepted work and human effort.

Unresolved: the user's actual eligible routes and quotas, local cancellation behavior, comparative planning/review quality, and whether any swarm reduces intervention versus a strong single-agent baseline. No credentials, live agent sessions, paid calls, deployments, or account changes were performed. No claim of four-, eight-, or forty-hour reliability is established.
