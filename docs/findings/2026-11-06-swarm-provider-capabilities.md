# Provider and harness capabilities for an evolving Stampede swarm

Research date: **2026-11-06**. Scope: the decision ticket **Establish supported provider and harness capabilities**. Findings distinguish documentation from local CLI observations; no authenticated workload, quota request, or credential inspection was performed.

## Main finding

A common loop can invoke all five installed harnesses non-interactively and retain a continuation identifier. Their authentication, permission, cancellation, and accounting contracts differ. A provider is an access/billing boundary; a model is a capability choice; a harness supplies tools, context, and execution behavior. Treating these as one interchangeable model string would lose material constraints.

**Consumer Google access has changed.** The official Gemini CLI project announced that individual Free, Google AI Pro, and Ultra requests stopped being served on June 18, 2026; enterprise Code Assist licenses and API-key authentication were unaffected. The current README directs individuals to Antigravity CLI. Some Gemini authentication/quota pages retain older individual-access descriptions, so those pages must not establish current subscription eligibility. [Transition announcement](https://github.com/google-gemini/gemini-cli/discussions/28017), [current project README](https://github.com/google-gemini/gemini-cli/blob/main/README.md).

Provenance check: GitHub's API identifies the announcement author `srithreepo` as a `CONTRIBUTOR` in the `Announcements` category, not proof of maintainer authority. The repository's current README independently confirms the transition; its raw content was verified through GitHub's API. That README also warns Gemini CLI is not tuned for Gemini 4+ and should not be used to benchmark those models. Actual account access remains untested.

## Local observations

Only `command -v`, `--version`, and `--help` were executed. Installed versions: **Codex 0.166.0; Claude Code 2.1.319; Gemini CLI 0.60.0; OpenCode 2.2.5; AGY 1.5.2**. Help confirmed the invocation/continuation flags above. These commands do not establish login, model availability, entitlement, quota, cancellation correctness, or successful execution. No configuration files were read.

## Design implications and unresolved facts

These are engineering inferences, not chosen policies:

- Use explicit session IDs; “continue latest” can select unintended work under concurrency. Preserve provider-native transcripts alongside portable project checkpoints.
- Normalize terminal outcomes and validate final evidence separately. Structured transport and exit zero do not prove the requested project outcome.
- No cross-provider concurrency reservation or atomic quota allocator was established. Shared subscription consumption, unknown quotas, and retries need a scheduler-owned policy.
- Process deadlines do not prove descendant or remote work has stopped. Cancellation, resource cleanup, and restart behavior require disposable live adapter probes for the pinned versions.
- Capture the actual harness/model version and authentication class per run, without secrets. A provider default or rolling alias can change between experiments.
- Before implementation, establish the user's actual provider/account set, supported access paths, overage settings, and capability probes. Do not infer these from installed executables.

No live sessions, billing tests, or cancellation/concurrency experiments were run. Documentation support is a design input, not an integration readiness claim.
